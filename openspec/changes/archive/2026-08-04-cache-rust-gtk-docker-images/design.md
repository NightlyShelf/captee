## Context

Captee currently uses fresh GitHub-hosted Linux runners. The Rust checks
install the toolchain and GTK/GtkSourceView development packages in several
parallel jobs, while the manual AppImage workflow installs a larger GTK and
packaging tool set. See `proposal.md` and the `ci-build-environments` spec for
the motivation and observable contract.

The image design must preserve the existing manual-only AppImage trigger,
support the Ubuntu 22.04-compatible release baseline, retain headless test
independence from a desktop session, and avoid making application runtime code
depend on Docker.

## Goals / Non-Goals

**Goals:**

- Prepare Rust and GTK dependencies once per image version and reuse them in
  all matching CI jobs.
- Keep a lean test image separate from the release build image.
- Make image references, cache invalidation, provenance, and fallback behavior
  explicit and auditable.
- Preserve the current test commands and manual-only AppImage packaging policy.

**Non-Goals:**

- Building or distributing the Captee AppImage automatically on every push.
- Replacing Cargo's incremental/cache behavior for local development.
- Bundling the host desktop session, display server, or runtime capture portal
  into either image.
- Supporting non-x86_64 image targets in this change.

## Decisions

### Two role-specific images

Publish `test` and `build` images from separate Dockerfiles or independently
maintained stages. The test image contains the pinned Rust toolchain, Cargo
metadata/cache inputs, GTK 4/GtkSourceView development headers, and tools needed
by fmt, clippy, and tests. The build image starts from the same compatible Linux
baseline but adds release-only AppImage, squashfs, ELF-patching, and packaging
prerequisites. Keeping them separate avoids putting release tooling and its
larger dependency surface into every test job.

An explicitly shared base layer may reduce registry storage, but role images
remain separately addressable and independently promotable. A single all-in-one
image was rejected because it increases pull size and expands test-job attack
surface.

### Immutable references and cache keys

Image tags are human-readable release labels only; workflows consume digest
references generated by the image publication workflow. The image build input
hash covers the Dockerfile, base-image digest, Rust toolchain file, GTK package
manifest, packaging-tool manifest, and relevant workflow scripts. Any change to
those inputs creates a new image version. Registry layer caching and GitHub
Actions cache metadata may accelerate publication, but neither substitutes for
the immutable consumer digest.

### Publication and validation workflow

Use a manually promotable or release-controlled workflow to build both images,
run architecture/toolchain/package smoke checks inside each image, scan layers
for secrets, and publish only after validation. The workflow emits a checked-in
or artifact-backed metadata record containing source SHA, image digests, base
digest, tool versions, and package versions. Registry credentials are exposed
only to the publish step with write scope; consumer workflows require read
scope.

### Container registry

Publish the role images to GitHub Container Registry as
`ghcr.io/nightlyshelf/captee/test` and `ghcr.io/nightlyshelf/captee/build`.
GitHub Actions uses `packages:write` only for the image publication job and
`packages:read` for consumers. The image contract remains portable if the
repository later adopts another OCI registry.

### Consumer workflow integration

The Rust checks use the test image for every existing job. The manual AppImage
workflow uses the build image and keeps its artifact upload behavior unchanged.
Each workflow performs a short preflight that prints the image digest and
verifies `rustc`, `cargo`, `pkg-config`, GTK/GtkSourceView metadata, and its
role-specific tools. If the registry image is unavailable, a clearly selected
runner fallback may install the existing prerequisites and must run the same
preflight; otherwise the workflow fails before tests or packaging.

### Fallback and rollback

Keep the current runner setup in a reusable fallback script during migration.
Consumer workflows can switch back to that script through a single workflow
variable or repository configuration value. Rollback changes the consumer
digest/reference only; it does not delete an image or mutate a previously
published digest.

## Risks / Trade-offs

- [Registry outage or rate limiting] → Keep the validated runner fallback,
  authenticate read-only pulls, and fail before work starts when neither image
  source is available.
- [GTK/base-image drift] → Pin the base image by digest and include package
  metadata in the image input hash and provenance record.
- [Large image pulls offset setup savings] → Keep test and build images
  separate, share only intentional layers, and measure pull plus job duration
  before and after adoption.
- [Stale toolchain cache hides missing dependencies] → Run preflight checks in
  every consumer job and fail on version or package mismatch.
- [Registry credentials leak through layers or logs] → Use ephemeral login
  steps, least-privilege tokens, secret scanning, and no credentials in
  Dockerfile `ARG`, `ENV`, or copied files.
- [Image publication becomes an unreviewed release path] → Require the same
  protected-branch review and CI policy for image-definition changes, and keep
  AppImage publication manual-only.
